## Why rc2, not a re-tagged rc1

`v1.0.0-rc1` was cut and pushed, then the clean-room procedure (§18) was run against it using `git archive` — extracting the *actual tagged git content*, not a filesystem copy — for the first time this session (P7/P8 clean-room runs had used `rsync` of the working directory, which includes local untracked files too, masking this exact class of bug). That run found `hash_submission.py --check` **FAIL** on the archive.

**Root cause**: `submission/evidence/file_hashes.csv` and `submission_manifest.csv` are generated by walking the filesystem, not by asking git what's tracked. `submission/artefacts/05_DDD_CONTEXT_MAP_Mahesh.md` — flagged since Phase 5 as an untracked, unclear-ownership file never included in any commit — was physically present on disk when those two files were last regenerated, so it got hashed and included in the manifest. `git archive v1.0.0-rc1` correctly omits it (it was never committed), so the archive's real file count didn't match what the hash-lock claimed, and `--check` correctly caught the mismatch.

**Fix**: the Mahesh file was moved to a holding location (not deleted — nothing about its unclear-ownership status changed), `submission_manifest.csv`/`file_hashes.csv` were regenerated against a filesystem state that now matches exactly what git tracks, the file was moved back, and a fresh `git archive` extraction of the new commit was re-verified. Tagged as `rc2` rather than force-moving the already-pushed `rc1` tag, since rewriting a pushed tag's history is exactly the kind of action that should never happen silently.

**Consequence for local development**: `tools/hash_submission.py --check` will now correctly report `FAIL` if run from a working directory that still has `05_DDD_CONTEXT_MAP_Mahesh.md` on disk (it does, locally, by design — see `CONVERSATION_SUMMARY.md`) — that's expected, not a regression. The authoritative check is always against a clean checkout of the tag, not the local working tree.
